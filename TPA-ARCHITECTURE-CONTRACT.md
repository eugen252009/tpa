# TPA / TPA.run Architecture Contract

**Binding project-owner decision. Read this before changing publishing,
repository, storage, signing, website or backend code.** Existing implementation,
historical qualification and conventional hosting designs do not override it.

> **TPA builds. TPA signs. TPA publishes.**
>
> Ordinary SSH servers copy and host files.
>
> TPA.run authenticates, authorizes, receives, deduplicates, stores, meters and
> serves the already-finished repository.
>
> Stripe and dashboards are optional integrations. The hosting server does not
> become another package builder or signing authority.

## 1. Component ownership

### TPA: independently usable developer-side builder and publisher

TPA runs on the developer's own system. It creates Debian packages from prepared
package directories or supported JSON definitions, initializes/processes package
structures, metadata and scripts, performs required Debian metadata/permission
normalization, builds completed `.deb` archives, creates complete APT repositories
and indexes, generates their websites/sidecars, signs with the developer/owner's
own configuration, inspects/verifies packages/repositories, and publishes finished
repositories to the selected destination. It must not require TPA.run.

Prepared directories are intentional, not an incomplete JSON implementation.
Projects may prepare/populate payloads using their ordinary staging operations,
combined with TPA initialization. Do not add a framework or extra full-payload
copy merely to stage application files. Do not require individual JSON entries
for every payload file, a mandatory JSON-only workflow, a new package-description
language, or a new filesystem sandbox. Symlinks and hardlinks are legitimate
construction mechanisms. Assess demonstrated unintended destructive operations
against the actual developer-controlled/untrusted-input boundary; ordinary link
following is not automatically a security vulnerability.

### TPA.run: host and optional optimized transfer destination

The core owns SSH authentication, repository-scoped authorization, content
reception, content-addressable storage/deduplication, transfer integrity checks,
repository generations/activation, exact byte preservation, HTTP hosting of APT
and the TPA-generated website, persistent usage metering, server-owned quotas
and resource policies, and appropriately authenticated management/integration
interfaces. A known content/chunk hash grants neither repository ownership nor
unauthorized read/write access.

The core is not a package or repository builder. It must not automatically rebuild
or repack DEBs, regenerate submitted indexes, rewrite package provenance, repair
inconsistent repositories, replace owner signatures, or sign again with a host
key. Reject invalid submissions. **Verification is not reconstruction.**
Reassembling transferred chunks into the exact advertised original files is
transport reconstruction and is allowed; inventing new APT metadata is not.

## 2. Finished repository before transport

```text
Application source / prepared tree / supported JSON
    -> project-owned payload preparation + TPA package construction
    -> completed .deb files
    -> local TPA repository generation and verification
    -> dists/ + pool/ + index.html + repository.json + required files
    -> developer-controlled signing and final verification
    -> destination-selected transport of the completed repository
```

The destination never decides who builds/signs the repository. A user can put
this complete signed output on an ordinary web server without TPA.run, a hosted
account or a database. The qualified finished artifact is the one transferred;
do not rebuild it unnecessarily for hosting.

Repository websites are generated by TPA from the same authoritative APT state,
not from a duplicate package database. TPA.run serves those original files.
The optional TPA.run account/repository/usage management website is a separate
API consumer, not the repository website or a mandatory core dependency.

## 3. Two transport strategies, same content and signing

### A. Ordinary SSH / SFTP

```text
finished client-built/client-signed repository
    -> standard authenticated SSH/SFTP
    -> ordinary remote directory -> ordinary HTTP hosting
```

No TPA-specific server software, remote database, TPA.run daemon, TPA identity
service, CAS/chunk protocol, deduplication or server signing is required.
Transfer necessary files with standard SSH-compatible semantics. Do not route
this strategy through the TPA.run protocol. Generic SSH authentication is the
ordinary server's responsibility; browser login is not a prerequisite.

### B. TPA.run enhanced SSH transport

```text
same finished repository
    -> authenticated restricted SSH protocol
    -> identity + repository-operation authorization + resource admission
    -> content-addressable missing-content negotiation
    -> transfer missing files/chunks only
    -> server verifies identifiers and reassembles exact original files
    -> complete generation verification and activation
    -> original repository bytes/signatures served over HTTP
```

A restricted subsystem/forced command is acceptable; a general shell is not
required. Authenticate identity separately from deciding repository permissions,
allowed operations and server quotas. Capability detection must identify the
enhanced transport without redefining repository contents or signing. Missing
capability must not silently downgrade authority or fall into server building.

## 4. Content-addressable transfer and storage

TPA inventories finished files and computes cryptographic content identifiers.
It may chunk data where useful. Over authenticated SSH, TPA.run determines what
is already available and requests only missing content. Verify every received
object against its advertised identifier, reconstruct original files exactly,
verify completeness/consistency, then activate a generation. Preserve bytes
through subsequent serving and recovery.

Use SHA-256 or an explicitly justified existing cryptographic content-addressing
mechanism. Whole-file reuse can be an initial optimization, but **chunk-level
reuse remains part of the target**. Measure fixed-size versus content-defined
chunking rather than choosing by assumption. Do not build an elaborate chunker
before measurements justify its details.

Chunk hashes are internal transfer/storage identifiers, not a package/release
identity, clean-hash, verified-release-hash, new signature, new APT metadata or
replacement for the completed DEB SHA-256. Reuse must remain authorized and
reference-accounted, with safe retention/garbage collection and recovery.

Support large repositories and individual payloads of tens/hundreds of gigabytes
without requiring the entire payload/repository in RAM. Prefer streaming,
bounded buffers, bounded/incremental inventories and reuse of existing files.
Do not automatically duplicate complete repositories before upload. Quotas may
limit an individual server deployment; they must not make whole-payload buffering
or mandatory copies the architecture.

## 5. Owner signing and provenance

The developer/repository owner controls APT signing. TPA signs before publication.
An ordinary SSH server and TPA.run can serve equivalent signed content. The host
may verify consistency, hashes, permissions, quotas and signatures against
explicit trust; it must not require the owner's secret key, a provider-owned
signing key or a second mandatory host signature.

Preserve `Created-At`, `TPA-Version`, explicit overrides and custom claimed origin
fields such as `Repository-URL`, `Git-Commit`, `Source-Revision`. These document
claimed origin/build context, not complete reproducibility. Dynamic provenance
is intentional; do not remove it merely to force identical builds. The SHA-256
of the completed `.deb` identifies its exact bytes. Do not introduce clean-hash,
release-hash, verified-release identity chains or additional mandatory provenance
manifests beyond existing requirements.

## 6. Metering and optional consumers

Core metering is persistent and independent of billing: physical stored data,
logical repository usage, transferred bytes, repository/package counts and
supported upload/download activity. Distinguish deduplicated physical storage
from logical/account usage and reserved in-flight resources. Do not embed
Stripe-specific rules into storage, transfer, authorization or usage engines.

Expose stable, authenticated management/integration interfaces for repositories,
identities/permissions, quotas, generations/artifacts, usage and server settings.
The same core supports:

```text
Minimal:         TPA.run core + SSH + HTTP
Self-hosted:     same core + optional dashboard
Managed hosting: same core + optional dashboard + Stripe adapter
```

Stripe may later consume usage/entitlement information through a dedicated
adapter. Neither Stripe nor a web dashboard is required to run the core. No
separate self-hosted repository implementation is permitted. Do not implement
Stripe as part of the architecture audit.

## 7. Canonical database direction

Prefer a **new unified canonical baseline** for required functionality, not a
complex bridge graph merely to preserve divergent development schema numbers.
Include identities/credentials, repository ownership/authorization, repositories,
generations, storage objects/chunk references, publishing/transfer state,
usage/quotas and demonstrated necessary optional integration state. Reuse useful
constraints and application authorization rules; a fresh schema does not remove
the need to integrate those features.

The owner reports no customer/user data requiring migration. Verify the actual
target environment before any destructive action. Absence of accounts does not
prove absence of durable repositories, signing material, configuration or
operational dependencies. Distinguish disposable development state from retained
live state. If none must be retained, fresh initialization is preferred.
Historical migrations/bridges are needed only for demonstrated retention needs,
not intrinsically because development Schemas17/20 collide.

**Never reset/delete a deployed database during an audit.** A future reset needs
explicit authorization, confirmed scope, retained state inventory and a recovery
plan. Do not create unnecessary tables merely to preserve historical branches.

## 8. Non-drift rules and eventual acceptance

Explicitly rejected: hosting-provider repository building/signing as standard
publication; individual-DEB ingestion as the replacement for finished repository
transport; TPA.run dependency for local building; CAS on ordinary SSH hosts;
mandatory Stripe/dashboard; new artifact identities/provenance chains;
per-file JSON payload declarations; unrelated frontend frameworks; mandatory
whole-payload isolation copies; historical migration complexity without retention
justification.

When current code conflicts: quote the requirement, show source evidence, explain
the conflict, propose the smallest compliant adaptation and mark unresolved facts.
Do not redefine the target as impossible because code was built differently.
Historical tests remain evidence of their exercised path, not architecture approval.

Eventual acceptance must demonstrate:

A. Complete local independent signed repository.
B. Ordinary SSH publication without TPA.run or CAS.
C. Authenticated SSH content-addressable TPA.run transfer of that same repository.
D. Exact hosted bytes including original signatures and websites.
E. Correct identity, repository authorization, generations, quotas and metering.
F. Removing Stripe/dashboard leaves core hosting operational.
G. No second authoritative package-building/repository-signing pipeline on host.

Qualify interruptions, resume, missing/incorrect objects, unauthorized reuse,
concurrent activation, retention/GC, restart/recovery, signed APT install/upgrade,
website consistency and fresh self-host install. No implementation phase may
quietly move client responsibilities back to the server.
